# 模型输出禁词拦截方案测试报告

面向业务与管理读者的完整汇报  2026年10月26日

## 1. 结论概览

我们已验证，修复后的完整拦截方案能够在本次测试范围内稳定工作。常规词表验证到10万条；已测输出中未发现注册禁词泄漏，普通请求也未观察到错误提示。词表从16条扩大到10万条时，热运行的首字延迟只小幅变化。断连后的恢复、10分钟预检查和60分钟连续运行测试均已完成。

这份报告回答五个问题：能拦得住吗、能放多少词、会不会拖慢回复、需要多少资源，以及多人使用或用户断开时是否稳定。结论基于合成测试数据和一张授权显卡上的隔离服务，可用于评估下一步业务验证，不构成生产上线容量承诺。

| 关注问题 | 已经测到的结果 | 适用范围 |
| --- | --- | --- |
| 拦截稳健性 | 标准编码回放1,004,968次，未发现漏拦 | 不同规模和重复回放，不能理解为百万条独立真实对话 |
| 词表容量 | 常规词表10万条；长短语3.5万条 | 达到当前已测范围，词条长度和资源预算也会影响容量 |
| 响应速度 | 首字P95约373毫秒→388毫秒 | 16条与10万条，同输入同到达率，每组32请求 |
| 短请求并发 | 16并发组全部完成 | 32与64并发大量触发准入拒绝 |
| 持续运行 | 10万词表，连续60分钟通过 | 中等输入，最多4个请求进入引擎同时处理 |
| 资源使用 | 服务进程内存合计约4.05 GiB | 包含运行时；不是词表本身的净增内存 |

### 建议如何使用这些结论

可以把修复版本作为下一阶段业务验证的候选。应保留两层拦截、有限排队和资源回收检查，再用真实业务词表与请求测试，并先约定用户可以接受的首字等待时间和完整回复时间。目前不宜把“测到16并发”直接写成上线承诺，也不宜把样本中的零漏拦写成任意输入下的100%保证。

阅读提示：正文使用通用表达。报告末尾解释常用术语，并提供原始报告、逐请求记录和数据包核验入口。

## 2. 方案如何工作

检查模型即将交付的输出  命中后停止并提示

我们把禁止输出的词和短语登记到一份词表中。模型生成内容后，系统在交付给用户之前检查新增输出。命中规则时，保留此前已经发布的内容，阻止补全禁词的内容和后续续写，结束生成，并由服务端追加固定提示。

### 两层检查共同组成完整方案

- 第一层检查模型已经确认有效的输出单元。模型采用一次预测多个输出单元的加速方式时，只检查经过确认、真正可能交付的内容。
- 第二层检查实际解码出的文本。它补上同一个词采用不同分词方式、或禁词藏在一个较长输出单元内部时的覆盖。
- 终止和提示只有一个明确的收尾流程。同一请求命中后不会反复追加提示，也不会在提示后继续输出正文。

固定提示为“【提示】我不能继续了。”。实验中的“花朵”等词仅用于合成验证，不代表它们在业务上有风险。判定依据是配置中的精确文字匹配；本方案没有加入语义理解、同义词推断或自动识别所有变体的能力。

### 为什么大词表仍能保持较低的运行开销

- 词表在服务就绪前完成编码和索引构建，后续请求复用已有索引。
- 大词表采用共享前缀的多模式查找结构。每次只推进新增内容的匹配状态，避免反复逐条扫描整份词表。
- 同一进程内共享只读规则，每个请求保留独立的匹配进度，减少重复构建并避免请求间串扰。
- 词表标识代替整份大词表在请求链路中反复传递；检查没有增加模型推理轮次。

### 本报告中的 bad_words 指什么

本项目复用了 bad_words 的部分词条编码方法，但实际评估的是自定义 Trigger Guard 加最终文本检查。本报告中的容量和性能数字属于这套实现，不能直接当作 vLLM 原生 bad_words 参数的性能或默认上限。

本次结果对应提前加载、重复使用的词表。每个请求都临时带入一份全新大词表的使用方式尚未验证。

## 3. 拦截效果与稳健性

把确定性回放和真实模型运行分开判断

完整方案在已测范围内没有观察到注册禁词泄漏或负例误提示。我们同时检查了“是否触发”与“最终向用户展示了什么”，并保留主动断连、拒绝和失败记录，避免只挑成功样本报告。

| 证据层 | 样本与结果 | 可以支持的判断 |
| --- | --- | --- |
| 标准编码的词条回放 | 1,004,968次应拦截机会全部拦截 | 已测标准编码路径的召回率为100%；包含重复规则与不同规模 |
| 替代编码和词内子串 | 138个正例均由最终文本检查捕获 | 仅靠编码匹配不够，最终文本检查必须保留 |
| 真实GPU负例 | 3284个完整返回的负例，未出现提示 | 这些已测普通请求没有被错误提示终止 |
| 真实GPU策略终止 | 600个完整返回包含一次固定提示 | 已观察的策略终止没有重复提示或提示后续写 |

在138个替代编码用例中，第一层编码匹配没有命中，第二层文本检查完成了拦截。这项结果说明两层检查有明确分工；不能删掉最终文本检查后继续引用完整方案的结果。

### 本轮真实请求的完整分母

| 开启保护的请求结局 | 数量 | 计数含义 |
| --- | --- | --- |
| 完整返回普通内容 | 3300 | 正常结束，未附加策略提示 |
| 完整返回策略提示 | 600 | 正常完成一次规则终止流程 |
| 客户端主动断开 | 63 | 故障注入用例，不算完整交付成功 |
| 准入拒绝 | 197 | 超出当前服务预算而拒绝，不算拦截成功 |
| 合计 | 4160 | 每个已发送请求都有明确终态 |

另有296个关闭保护的诊断请求用于对照，不纳入安全效果判断。整轮共4456个请求，所有请求均有终态记录。上表600次完整提示与另外6次在主动断连前已观察到的提示分开，避免把未完整交付的流算成成功。

### 正确率需要怎样表述

可以说“已测样本中未发现漏拦或误拦”。不能说“真实使用保证100%”。CPU回放覆盖了已测词表的标准编码，但真实GPU请求仅覆盖部分固定词条与模板，未逐词验证全部10万条在自然对话中的表现。真实运行没有全量记录每一步内部候选，因此没有据此计算一个通用的自然对话拦截召回率。

69项CPU和模拟回归还覆盖了请求交错、重复结束、跨输出块匹配、字符边界、输出合并、断连与清理等场景；8项引擎分类夹具与7项负载工具测试也通过。模拟通过和真实GPU通过分别保留证据。

## 4. 词表容量与资源占用

容量同时受到条数  词条长度和索引大小影响

| 词表类型 | 最大成功测试条数 | 成功测试的最长词条 |
| --- | --- | --- |
| 常规合成词表 | 100000条 | 32个字符 |
| 大量共同前缀的词表 | 100000条 | 41个字符 |
| 长短语词表 | 35000条 | 156个字符，约30个模型输出单元 |

常规与共同前缀词表到达预设的10万条扫描上限后停止，尚未找到硬件的真正极限。长短语在35000条通过；测试到37500或40000条时触及当前400万个索引状态的预算。这个结果说明词条变长也会增加资源消耗，不能只按词条数量估算容量。

### 配置允许的长度与已经验证的长度

代码当前允许单条最多4096个字符，整份词表总计最多1600万个字符，条数最多10万。成功加载并回放验证的最长词条为156个字符。4096是配置允许上限，不代表本次已经完成该长度词条的实际拦截验证。超限配置会明确报错，未采用静默丢弃部分词条的方式通过测试。

| 内存测量对象 | 实测值 | 如何理解 |
| --- | --- | --- |
| 10万条常规词表的CPU测试进程峰值 | 1.450 GiB | 包含Python、分词器、规则和索引等 |
| 10万条共同前缀词表的CPU测试进程峰值 | 1.498 GiB | 同一类单进程测试口径 |
| 3.5万条长短语词表的CPU测试进程峰值 | 2.619 GiB | 较长词条占用更多索引空间 |
| 真实服务进程内存合计 | 约4.05 GiB | 多个服务进程的RSS合计，含运行时 |
| 真实运行GPU显存采样峰值 | 37100 MiB，约36.2 GiB | 包含模型和生成缓存，主要不是禁词表 |

词表检查主要使用CPU内存。我们尚未单独剥离索引本身的净增内存，因此不能把1.45 GiB全部算成禁词表开销，也不能用服务总内存减去一个未经配对的基线得出精确增量。多进程的RSS还可能重复计入共享页。

### 一次性准备成本

10万条常规词表的CPU测试中，第一层编码规则索引构建中位数约11.0秒，第二层文本索引构建约1.9秒。这些是词表准备阶段的成本，和后续请求的响应时间分开计量；不能直接当作整套服务的启动时间。

多API进程、每个用户单独持有词表、在线频繁切换词表的总资源成本尚未测量。

## 5. 词表扩大后的响应速度

热运行的延迟变化较小  冷加载成本单列

在相同输入、相同请求到达率和同一模型配置下，词表从16条增加到10万条，首字P95约增加15毫秒，完整回复时间基本不变。该结果支持“大词表在本次预加载场景下没有明显拖慢请求”，不支持“词表扩大永远没有成本”。

| 短请求指标 | 16条词表 | 10万条词表 | 变化 |
| --- | --- | --- | --- |
| 首字等待时间P95 | 373毫秒 | 388毫秒 | 约增加15毫秒，3.9% |
| 完整回复时间P95 | 3.447秒 | 3.437秒 | 约减少10毫秒，基本相当 |
| 测量窗口内完成请求数每秒 | 1.790 | 1.783 | 约下降0.36% |

首字等待时间指发出请求到收到第一段可见内容的时间。P95是用于观察较慢请求的指标，可以理解为约95%的样本不超过该时长。它不是平均时间，也不能由很少样本稳定估计极端最慢情况。

### 这组对比怎样保证可比

- 两边使用相同的普通问题、输入长度和输出上限，词表扩大时加入额外规则。
- 输入约512个模型处理单元，回复上限64个；固定计划到达率约2.09请求每秒。
- 两边都开启完整保护，正式组各32个请求，全部完成且没有策略提示。避免把提前截短回复误当成提速。
- 词表完成加载与验证后才开始正式计时，因此这里是热运行结果。

### 中等长度输入的补充观测

| 正常完成的负例指标 | 16条词表 | 10万条词表 |
| --- | --- | --- |
| 首字等待时间P95 | 1.577秒 | 1.575秒 |
| 完整回复时间P95 | 13.564秒 | 13.637秒 |

补充组使用约2048个输入单元、最大256个输出单元，最多4个请求同时进入引擎。每边60个混合请求，其中54个为普通负例。完整回复P95约增加0.073秒，即0.54%。不同输入长度的时间不能直接相互比较。

较早的同配置词表扫描，在10万词表、客户端并发8和16下各做了三次短组重复，延迟与吞吐也落入预设的相对比较门槛。这些历史短组单独保留，不与本轮修复后的数据混算；旧的未修复异步配置曾失败。

本轮同速对比仍是小样本，未提供统计显著性或生产延迟保证。没有完成随词表规模变化的真实“命中后提示送达时间”完整曲线。

### 突发到达也有单独测试

固定速率、随机到达和每批16请求的突发分开测试。较高两档突发分别出现2/32和5/32准入拒绝，对应计划平均到达率约2.61和3.13请求每秒。其余相关短筛选点完成；每组仅32请求，不能据此确定长期最大吞吐。

## 8. 历史问题与当前结论边界

保留失败证据  结论仅适用于修复后的已测版本

### 曾经发生什么问题

较早的未修复异步并发实验，在随机断连组中出现引擎异常退出，日志包含GPU索引越界和GDN分类断言。当时立即停止后续压力与长稳测试，并保留失败记录。此前还修复过响应刚开始就断连时，服务未完整释放名额和缓冲的问题。

### 现在确认了什么

归因实验在没有Guard运行时补丁、没有客户端断连、只有两个并发请求的条件下，独立复现了GDN分类断言。问题发生在输入处理的尾部只剩一个待处理单元时，引擎将它错误归类。单独修复后，相同边界输入通过；随后本轮将该修复应用到独立V2副本，完成了全部40个主线正式组、边界与开关对照、故障恢复和10加60分钟稳定性测试。

本轮没有复现GDN断言，也没有再出现GPU索引越界。不过，历史GPU索引越界的原因仍未被独立确定。因此可以确认GDN缺陷不需要Guard也能触发，但不能把“本轮未出现错误”扩大成“历史所有错误都已彻底归因”。

### 仍需要保留的条件

- 词表为合成词条，真实业务用词、绕写方式和自然对话分布尚需验证。精确文字匹配不自动覆盖同义表达和语义风险。
- 10万条是当前已测上限；真实GPU并未逐词覆盖全部10万条，4096字符词条也尚未完成实际拦截验证。
- 没有业务约定的绝对延迟和成功率目标，短组样本量不足以承诺生产最慢请求表现。
- 多用户各自独立词表、频繁在线更新、多API进程、多GPU、工具调用和多模态输出尚未验证。
- 强制中断引擎进程后的自动恢复、完整模型数值等价，以及所有可能的分词形式尚无完整证明。

### 建议下一步怎样验证

- 先确定真实业务词表和典型问题，确认要覆盖的大小写、符号、空格及其他变体规则。
- 约定可接受的首字等待、完整回复时间和拒绝率，再围绕候选并发做独立重复，确认稳定可用区间。
- 单独测词表索引净增内存，以及更新词表和每用户独立词表的成本。
- 保留现有两层检查和过载保护；对历史GPU越界准备独立取证，不把原因未明的故障合并解释。

本次交付是隔离实验的验证结果，没有生产切流。实验结束后，拥有的进程全部退出，测试显卡回到4 MiB且无计算进程；未改系统驱动、全局依赖或其他生产服务。

## 9. 测试口径与证据入口

便于复核  不要求汇报读者掌握实现代码

| 常见词语 | 本报告中的含义 |
| --- | --- |
| 词表条数 | 登记的禁止字符串数量；一个条目可以是词，也可以是长短语 |
| token 模型处理单元 | 模型拆分文本后的单位，不等同于汉字数或英文字数 |
| 客户端并发 | 客户端同时尚未结束的请求数，可能包含排队和即将被拒绝的请求 |
| 引擎准入 | 当前允许进入引擎处理的请求数上限 |
| 完整返回 | 按协议正常结束，可能是普通内容，也可能是一次策略提示 |
| 主动断连 | 测试工具有意中止连接；不算系统错误，也不算完整交付 |
| 准入拒绝 | 超过当前预算时明确拒绝新请求；不算拦截成功 |
| P95 | 用于观察较慢请求的经验百分位；小样本仍有波动 |
| GiB 和 MiB | 内存容量单位；1 GiB等于1024 MiB |

### 执行范围和完整总账

硬件为隔离测试机的一张48 GiB显卡；模型、分词器和量化配置保持一致。推理引擎基于vLLM 0.17.0的固定源码，使用独立副本应用GDN分类修复，原始安装和原V2包未改。主线使用多输出预测深度3及异步调度，最大上下文4096；本文所有性能数字都受该配置和工作负载约束。

修复复测共9个GPU实例，40个主线正式组。包括预热、检查和诊断对照，实际发送4456个请求：4176个完整返回、83个主动断连、197个准入拒绝，没有新增结果未知。主线正式组单独为3224个完整返回、43个主动断连和165个拒绝。

累计实例运行约6622.9秒，预留8312个请求额度；预留额度包含最终没有消耗的长稳请求上限，不能当作实际发送量。启动前的脚本导入失败以及测试夹具修正记录均保留。历史未修复版本失败的数据没有与本轮混合或删除。
